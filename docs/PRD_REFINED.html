1. Problem & Positioning

A developer portfolio's actual job is to answer one question fast: can this person build production-quality software? Most portfolios answer it badly — a static grid of GitHub links with no narrative, no depth, and no proof of judgment under real constraints.

This product answers it directly. The portfolio itself is the proof: a working monorepo with a real auth system, a real database, a real AI layer with cost controls and injection defenses, and a design system that reflects a specific cultural identity rather than a generic template. A hiring engineer who opens the dashboard, tries the AI chat, or reads the case studies is evaluating the candidate's actual engineering — not a claim about it.

The subject is a self-taught full-stack engineer from Kano, northern Nigeria — a mathematics graduate and former professional tailor. Those three backgrounds aren't biographical trivia; they're load-bearing in the product's design decisions (see §7, Design Rationale).

2. Goals

Primary

  • Convert a hiring manager or client's first 90 seconds on the site into genuine interest
  • Demonstrate full-stack depth: auth, data modeling, API design, AI integration, security hardening
  • Make the cultural identity (Hausa design language) a structural part of the product, not a skin

Secondary

  • Own the content pipeline (blog, projects) via a real admin dashboard — no CMS dependency
  • Build a subscriber base for future launches with zero-friction opt-in
  • Keep hosting cost near-zero at low traffic (Vercel + Railway + Neon free tiers)

3. Non-Goals

  • Multi-tenant / multi-user portfolio platform — this is a single-owner product, not a SaaS others sign up for
  • A full CMS with rich media pipeline — the blog editor is intentionally simple (MDX textarea + AI assist), not a WYSIWYG
  • Real-time collaboration on blog drafts — single-admin, no concurrent-editing conflict resolution needed
  • Native mobile app — the web experience is responsive-first and sufficient

Not in the original FR list. The v1 approach (a "copy email to clipboard" button) was replaced with a full system once it became clear a real inbox — not a clipboard trick — was table stakes for a product meant to demonstrate production judgment: ContactMessage model, public POST /contact with honeypot + rate limiting, and a dashboard inbox with read/unread state and reply-via-mailto. 5. AI Feature Specification

Seven OpenRouter-backed models, routed through one shared service, used across five distinct product surfaces:

Every model is selectable per-feature via a shared ModelSelector/ModelDropdown component. Every admin endpoint hard-caps max_tokens server-side regardless of client input (see SEC-08 in the security report). The public chat endpoint sanitizes every inbound message against known prompt-injection patterns before it reaches the model (SEC-03).

7. Design Rationale (Summary)

Full detail lives in DESIGN_DECISIONS.html. In brief: the three professional identities behind this product — mathematician, tailor, self-taught engineer — map directly onto specific product decisions rather than sitting in an "About" paragraph alone.

  • Mathematics → the D3 visualizations, the type-safety discipline (zero any across the codebase), the explicit state-machine thinking in components like the contact form and AI chat.
  • Tailoring → the Desert Monarch design system's restraint — a tailor doesn't add embellishment that doesn't serve fit; every Hausa motif in this product is load-bearing UI (a loading spinner, a nav indicator, an avatar frame), never decoration for its own sake.
  • Self-taught → the documentation discipline itself — this PRD, the changelog, the bug report, and the git history exist because a self-taught engineer's proof of process matters as much as the output.

8. Risks & Mitigations

RiskMitigation
OpenRouter cost overrun from an abusive userPer-endpoint rate limiting + server-side max_tokens ceiling regardless of client input (SEC-08)
Contact form / subscribe abused as a spam vectorHoneypot field, rate limiting, disposable-domain blocklist (SEC-07)
Admin account compromiseShort-lived (15 min) access tokens, httpOnly refresh cookie, bcrypt hash, startup-enforced 32-char minimum JWT secret (SEC-06)
Cultural motifs read as decorative rather than intentionalEvery Hausa component is wired to actual UI function (see §7) — verified during design review, not left to interpretation
Monorepo package resolution breaking on a fresh clonepnpm-workspace.yaml + properly built dist/ output for shared packages, verified against a real build (see build 0.7.0 in CHANGELOG.md)

9. Out of Scope for Current Version

  • Multi-language i18n (Hausa-language toggle) — noted as a plausible future direction, not committed
  • A public API for third parties to query project/blog data — the API is currently first-party only
  • Automated CI/CD pipeline definition — deployment is currently manual (Vercel/Railway git-push triggers only)
