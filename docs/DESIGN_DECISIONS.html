1. Visual Design System

The design isn't a generic dark-mode-toggle template with a color swap. Every choice traces back to one of the three professional identities behind the product.

Desert Monarch palette — why warm clay + indigo, not a typical developer-portfolio blue/purple

Shipped

Clay (#b27343) references the mud-and-lime architecture of Kano's old city — the same material used in the walls, arches, and Zankwaye plasterwork the SVG component library is drawn from. Indigo (#1a3f6f) references the Kofar Mata dye pits, a specific, real, 500-year-old dye works in Kano — not a generic "African" color association. Indigo is deliberately reserved, used only for the SaaS era of the projects section and for data-visualization accents, so it reads as a distinct signal ("this is live, this is current") rather than being diluted across the whole UI.

ChoseTwo-color system with strict semantic reservation (clay = brand default, indigo = "current/live" signal only)
RejectedA single accent color used everywhere — simpler, but loses the ability to signal "this project is different from the others" at a glance

Hausa components as functional UI, not decoration

Shipped

Every one of the 8 SVG components has a real job. This was a deliberate constraint set at the start: if a motif can't be justified as solving an actual UI problem (loading state, active-nav indicator, section divider, avatar frame), it doesn't ship. This is the tailoring identity showing up directly — a tailor doesn't add a design element that doesn't serve fit or function.

LaujeSpinnerLoading indicatorA generic spinner communicates nothing; this one is recognizable as this product's specific loading state, and rotates like the parasol it's drawn from

Typography stack — four fonts, not one

Shipped

Playfair Display (headings) carries the "crafted, considered" register. DM Sans (body) is chosen specifically for its geometric-but-warm letterforms — legible at small sizes without feeling clinical. Bricolage Grotesque is reserved only for numeral-heavy contexts (stat cards, dashboard metrics) because its numeral design is more distinct at a glance than DM Sans's. JetBrains Mono appears only in genuinely technical contexts (the terminal easter egg, code snippets, tech-stack chips) — using a monospace font outside those contexts would undercut the signal that "this is code" when it actually appears.

2. Architecture Decisions

Every major structural choice, with what was rejected and why.

Separate Fastify API vs. Next.js API routes / Server Actions

Shipped

Next.js can absolutely host an API within the same app. A standalone Fastify service was chosen instead for two concrete reasons: (1) the API needed to be independently deployable and scalable from the frontend — Vercel's serverless model isn't ideal for long-lived SSE streams (the AI chat endpoint holds a connection open for the duration of a streamed response), while Railway's persistent-process model handles that naturally; (2) keeping a hard boundary between "public frontend" and "backend with database credentials" is a security posture worth the extra deployment complexity, not just a style preference.

ChoseStandalone Fastify API, deployed separately, communicating over REST + SSE
RejectedNext.js Route Handlers / Server Actions — simpler single-deploy story, but couples frontend and backend scaling, and SSE inside serverless functions is fragile

pnpm workspaces + Turborepo vs. two separate repos

Shipped

A shared @devcraft/types package gives both the API and the frontend one source of truth for every response shape (ApiResponse<T>, Project, AnalyticsOverview, etc.) — a field rename in the database layer becomes a compile error in the frontend immediately, rather than a silent runtime mismatch discovered in production. That guarantee is worth the added monorepo tooling complexity (see the build-pipeline issues documented in BUGS_AND_SECURITY_REPORT.html, build 0.7.0 — this complexity is real and did bite once).

Vanilla Three.js vs. React Three Fiber for the hero

Shipped

The hero background is a single, self-contained, imperative animation loop with no need to participate in React's render cycle beyond mount/unmount. React Three Fiber's declarative scene graph is genuinely valuable when 3D content needs to react to component state or compose with other React components — neither applies here. Vanilla Three.js inside one useEffect, loaded via next/dynamic(() => import(...), { ssr: false }), keeps the bundle smaller (no R3F/drei dependency) and the code simpler for a single, isolated visual.

// components/portfolio/Hero.tsx
const HeroThreeJS = dynamic(() => import("./HeroThreeJS"), {
  ssr: false,
  loading: () => <div className="absolute inset-0 sawaki-bg opacity-60" />,
});
// CSS fallback renders instantly; WebGL canvas swaps in once the
// bundle loads — no blank flash, no SSR/hydration mismatch risk

D3 for computation, React for the DOM — never D3 for DOM manipulation

Shipped

D3 and React both want to own the DOM, and letting D3 mutate elements React also renders is a well-known source of bugs (React's virtual DOM diff and D3's imperative .attr() calls fight each other). The pattern used throughout D3Charts.tsx: D3 computes scales, paths, and layout math; the actual SVG elements are still written by D3's selection.append() calls into a ref'd container, but that container is fully owned by the effect and never touched by React's render output afterward — React only renders the wrapping <svg ref={svgRef}> once, and D3 populates it imperatively inside useEffect, tearing down and rebuilding on every relevant dependency change.

MDX blog storage — database column, not filesystem

Shipped

A common Next.js blog pattern stores MDX as files in the repo, rebuilt at deploy time. That's incompatible with an admin dashboard that publishes posts at runtime without a redeploy. BlogPost.content is a plain String column holding raw MDX text, rendered at request time via next-mdx-remote/rsc. The trade-off is losing filesystem-based version history for posts (mitigated by the admin UI being the only write path, with `updatedAt` tracked) in exchange for instant publish with zero deploy.

3. AI Layer Design

One shared OpenRouter service vs. per-feature API clients

Shipped

All five AI-powered features share one openrouter.service.ts — one model registry, one SSE helper, one client instance. The alternative (each feature managing its own OpenAI-SDK-compatible client) would duplicate the token-ceiling logic, the model-registry typing, and the streaming boilerplate five times, and would make a future provider swap five times the work.

export const MODELS = {
  "openai/gpt-4o-mini": { maxTokens: undefined, ... },
  "deepseek/deepseek-r1-0528": { maxTokens: 10000, ... },
  // ...7 total
} satisfies Record<string, ModelConfig>;

// `satisfies` (not `: Record<string, ModelConfig>`) is deliberate:
// it validates every entry against ModelConfig while keeping each
// object key as its own literal string, so `keyof typeof MODELS`
// stays a 7-member union instead of widening to plain `string`.
export type ModelId = keyof typeof MODELS;

Server-Sent Events vs. WebSockets for streaming

Shipped

Every streaming AI response is one-directional (server → client) and short-lived (seconds to tens of seconds). SSE is purpose-built for exactly that and needs no extra client library, no connection-upgrade handshake complexity, and degrades to a normal HTTP request/response in dev tools for easy debugging. WebSockets would be the right call if the product needed bidirectional real-time features (live collaboration, presence) — it doesn't.

Prompt-injection defense — pattern matching, not a second model call

Shipped

A more thorough defense would run every user message through a separate classifier model before it reaches the main chat model. That doubles latency and cost on every message for a public, unauthenticated endpoint. The chosen approach — regex pattern matching against known injection phrasings, plus a trailing system-message reminder appended after the user's turns — is a pragmatic middle ground: it catches the common, unsophisticated attempts (which is the realistic threat model for a portfolio chat widget, not a high-value target) without adding a second model round-trip to every request.

4. Edge Cases

Specific failure modes the implementation handles explicitly, and how.

Embedded project demo — target site blocks iframe embedding

A live project set as a SaaS-era demo might send X-Frame-Options: DENY, which fails silently from JavaScript's perspective — there's no onerror event for this. The iframe's load event actually fires even when the content is blocked (some browsers show a blank frame, others show a native "refused to connect" page inside the frame), so a same-origin content check can't reliably detect the block either.

const launch = () => {
  setState("loading");
  // If onLoad hasn't resolved state within 8s, assume the
  // target is blocking embedding rather than being slow —
  // a real page load, even a slow one, fires onLoad well
  // before this; this is a heuristic, not a certainty
  timeoutRef.current = setTimeout(() => {
    setState(s => s === "loading" ? "blocked" : s);
  }, 8000);
};

The "blocked" state shows a screenshot fallback with a direct "open in new tab" link, rather than leaving a permanently-spinning loader.

Scroll reveal — elements added to the DOM after initial mount

Project cards and blog list items render from an async data fetch; by the time that data arrives, the initial IntersectionObserver.observe() pass has already run and missed them entirely.

const observe = () => {
  document.querySelectorAll(".reveal:not([data-rv])")
    .forEach(el => { io.observe(el); el.dataset.rv = "1"; });
};
observe(); // initial pass

const mo = new MutationObserver(() => observe());
mo.observe(document.body, { childList: true, subtree: true });
// re-scans on every DOM mutation, but the [data-rv] marker
// means already-observed elements are skipped — O(new elements)
// per mutation, not O(all elements)
Contact form — bot submissions vs. legitimate fast typers

A honeypot field (a form input hidden from sighted users via CSS, that legitimate users therefore never fill in) is the chosen defense over a time-based "too fast to be human" check, specifically because time-based checks produce false positives against password managers and browser autofill, which fill a form in milliseconds — exactly the pattern a naive bot-detector would flag.

<input
  type="text" name="website" value={form.website}
  onChange={change("website")} autoComplete="off" tabIndex={-1}
  aria-hidden="true"
  style={{ position: "absolute", left: "-9999px", width: 1, height: 1, opacity: 0 }}
/>
// Real users never see or fill this. Simple scraping bots that
// fill every input on a page will. Server-side: if (website) →
// respond 201 as if successful (don't reveal the check exists),
// but skip the database write and the email.
JWT refresh — 401 mid-request vs. 401 on page load

Two different situations both produce a 401 from the API, and conflating them causes bugs: (1) the admin's access token expired naturally during an active session — should silently refresh and retry; (2) the admin was never logged in / the refresh cookie itself is invalid — retrying forever would loop.

if (res.status === 401 && path !== "/auth/login") {
  const refreshed = await fetch(`${BASE}/auth/refresh`, {...});
  if (refreshed.ok) {
    // case 1: rotate token, retry original request once
    setToken(data.data.accessToken);
    return (await fetch(`${BASE}${path}`, {...})).json();
  } else {
    // case 2: refresh cookie itself is gone/invalid — give up,
    // clear cached token, let the caller's UI redirect to login
    setToken(null);
  }
}
Dark mode toggle — D3 charts already painted before the toggle fires

CSS custom properties resolve to different hex values under .dark, but SVG elements D3 already drew have those resolved values baked into their fill/stroke attributes as static strings — they don't "listen" to CSS variable changes the way an element styled purely via CSS would.

function useDarkMode(): boolean {
  const [dark, setDark] = useState(false);
  useEffect(() => {
    const check = () => setDark(document.documentElement.classList.contains("dark"));
    check();
    const mo = new MutationObserver(check);
    mo.observe(document.documentElement, { attributes: true, attributeFilter: ["class"] });
    return () => mo.disconnect();
  }, []);
  return dark;
}
// every chart: const dark = useDarkMode();  useEffect(() => {...}, [data, dark]);
// `dark` doesn't need to be read inside the effect — its only job
// is forcing the effect to re-run (and thus re-read getCSSVar())
// when the class changes
Highlight-to-share — selection spans multiple DOM nodes, or falls outside the article

The Selection API's getRangeAt(0) can return a range whose commonAncestorContainer is outside the blog content wrapper entirely (e.g., the user drags a selection from the article into the sidebar). Rendering a highlight card for that would be nonsensical.

const range = sel.getRangeAt(0);
if (!contentRef.current.contains(range.commonAncestorContainer)) {
  setSelection(null); // silently ignore — no popup, no error
  return;
}
// length bounds also enforced: 20–600 characters. Below 20,
// the quote card would look absurd; above 600, it would be
// truncated so aggressively the "share" feature loses its point
Analytics referrer field — used as free-form input from the browser's document.referrer

This value originates from the visitor's browser and is fully attacker-controllable (a crafted link, a malicious redirect chain) before it ever reaches the API. It's stored, and later rendered in the admin dashboard — a stored-XSS path if not handled carefully, even though React escapes by default (defense in depth, not reliance on a single layer).

function sanitizeReferrer(referrer?: string): string | null {
  if (!referrer) return null;
  try {
    const u = new URL(referrer); // throws on anything not a real URL
    return (u.protocol === "http:" || u.protocol === "https:")
      ? referrer.slice(0, 500) : null;
  } catch { return null; } // malformed input discarded, not stored
}

5. State Management Patterns

No global state library

Shipped

Neither Redux/Zustand nor React Context-as-global-store is used anywhere in this codebase. The admin access token lives in a module-level variable backed by sessionStorage (see lib/api.ts); every other piece of state is either server data fetched per-page (React Server Components, no client cache needed) or genuinely local component state. The product's actual state-sharing needs turned out to be small enough that a global store would have added indirection without solving a real problem — this was verified, not assumed, by noticing every attempted "shared state" need (theme, auth token) had a simpler dedicated solution.

Form state — typed generic setter, not (form as any)[key]

Shipped

Both dashboard CRUD forms (projects, blog) originally used an untyped index-signature pattern to update arbitrary fields, which silently defeated the type checker on every field write. Replaced with a generic helper that keeps full type safety:

const setField = <K extends keyof ProjectFormState>(
  key: K, val: ProjectFormState[K]
): void => {
  setForm(prev => ({ ...prev, [key]: val }));
};
// call site: setField("published", true) — `val`'s type is
// inferred/checked against exactly that field's declared type,
// not `any`
