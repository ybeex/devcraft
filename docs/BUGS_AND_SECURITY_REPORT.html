Build Pipeline & Runtime Correctness

v0.7.0

Surfaced by the first real npm run build against a live environment (Prisma 7.8.0, Zod 4.4.3). Four compiler errors were reported; three of the four fixes below go beyond the literal error message because silencing just the reported line would have produced a build that succeeds and then crashes at node dist/server.js.

BLD-01
TS6059 — file outside rootDir, and the runtime break it was hiding
CRITICAL

apps/api/tsconfig.json path-mapped @devcraft/db straight at packages/db/index.ts — raw TypeScript source, outside apps/api's rootDir: "src". Fixing only the tsconfig would make tsc pass, but packages/db/package.json's main field still pointed at that same .ts file — plain node cannot execute TypeScript, so node dist/server.js would fail immediately after a "successful" build. The real fix gives packages/db and packages/types real compiled output and points every reference at that.

Before — packages/db/package.json
{
  "name": "@devcraft/db",
  "main": "./index.ts",
  "types": "./index.ts",
  "exports": {
    ".": {
      "types":   "./index.ts",
      "import":  "./index.ts",
      "require": "./index.ts",
      "default": "./index.ts"
    }
  }
  // no "build" script —
  // nothing ever compiles this
}
After — packages/db/package.json
{
  "name": "@devcraft/db",
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types":  "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js"
    }
  },
  "scripts": {
    "build": "tsc -p tsconfig.json"
  }
}
Before — apps/api/tsconfig.json
{
  "compilerOptions": {
    "rootDir": "src",
    "paths": {
      "@devcraft/db": [
        "../../packages/db/index.ts"
      ]
    }
  }
}
After — apps/api/tsconfig.json
{
  "compilerOptions": {
    "rootDir": "src"
    // paths override removed —
    // resolves via package.json
    // exports like any normal dep
  }
}

Also added "dependsOn": ["^build"] to Turborepo's dev task (it already existed on build), so pnpm dev compiles packages/db and packages/types automatically before starting either app — otherwise the very first pnpm dev after this change would fail the same way, just in dev mode instead of prod.

BLD-02
Zod v4 z.record() now requires two arguments
HIGH

Zod v3 allowed z.record(valueSchema), implicitly treating keys as string. Zod v4 requires the key schema explicitly. The installed version had drifted to v4.4.3 while package.json still declared a v3 range, so this passed locally and failed the moment a fresh install picked up the version actually declared as compatible.

Before — projects.routes.ts:14
metrics: z.record(
  z.union([z.string(), z.number()])
).nullable().default(null),
After — projects.routes.ts:15
metrics: z.record(
  z.string(),
  z.union([z.string(), z.number()])
).nullable().default(null),
BLD-03
Prisma nullable-Json field rejects bare null
HIGH

A Json? column can hold either a SQL NULL or a literal JSON null value — two different things. Prisma's generated types force you to be explicit about which one you mean via the Prisma.JsonNull sentinel; a plain JavaScript null (exactly what Zod's .nullable().default(null) produces) doesn't satisfy the generated NullableJsonNullValueInput type.

Before
const project = await app.prisma
  .project.create({
    data: parsed.data
    // metrics: null goes straight in
  });
After
function toPrismaMetrics(m: Record<string, string|number> | null) {
  return m === null ? Prisma.JsonNull : m;
}

const project = await app.prisma
  .project.create({
    data: { ...parsed.data,
      metrics: toPrismaMetrics(parsed.data.metrics) },
  });

Same helper applied at the .update() call site — both write paths funnel through it.

Module Resolution & Type-Safety Sweep

v0.6.0

A full-repository pass triggered by a real Cannot find module '@devcraft/types' error, which turned into a complete sweep for every remaining any type across both apps and the API.

MOD-01
pnpm-workspace.yaml didn't exist
CRITICAL

The root package.json had a "workspaces" field — that's a Yarn/npm convention. pnpm only reads pnpm-workspace.yaml. Without it, pnpm install never linked @devcraft/types or @devcraft/db into either app at all.

Before
devcraft/
├── package.json   ("workspaces": [...])
├── apps/
├── packages/
  (no pnpm-workspace.yaml anywhere)
After — pnpm-workspace.yaml (new file)
packages:
  - "apps/*"
  - "packages/*"
MOD-02
notFound() narrowing — "post/related do not exist on type '{...} | null'"
HIGH

Calling notFound() without an explicit return doesn't reliably narrow the surrounding variable to non-null under strict mode — TypeScript can't always prove every code path exits.

Before
const data = await getPost(params.slug);
if (!data) {
  notFound();
}
// data is still `{...} | null` here
const { post, related } = data; // ERROR
After
interface BlogPostData { post: BlogPost; related: RelatedPost[]; }

const data: BlogPostData | null = await getPost(params.slug);
if (!data) {
  return notFound();
}
// data is now BlogPostData — narrowed
const { post, related } = data;
MOD-03
fetch() + Next.js next cache option not in RequestInit
HIGH

Repeated across five server component pages — Next.js augments the global fetch with a next: { revalidate } option that the standard TypeScript RequestInit type doesn't know about.

Before (× 5 files)
const res = await fetch(url, {
  next: { revalidate: 300 } // ERROR:
  // 'next' does not exist in type
  // 'RequestInit'
});
After — lib/fetch.ts (new)
export type NextFetchInit = RequestInit & {
  next?: { revalidate?: number|false; tags?: string[] };
};

export async function fetchJSON<T>(
  url: string,
  opts: { revalidate?: number } = {}
): Promise<T | null> {
  const res = await fetch(url, {
    next: { revalidate: opts.revalidate ?? 300 },
  } as NextFetchInit);
  ...
}

The one necessary cast now lives in a single contained helper instead of being repeated (and potentially typo'd) five separate times.

MOD-05
Prisma enum cast via as any, duplicated across two files
MEDIUM

Device detection logic was inline in both analytics.routes.ts and blog.routes.ts, each casting a plain string to Prisma's DeviceType enum with as any to silence the type checker.

Before (duplicated in 2 files)

  return DeviceType.DESKTOP;

MOD-07
Insights parsing used let result: any
MEDIUM

The AI model can return a bare array or wrap it in {"insights": [...]}" / {"data": [...]}" — genuinely not knowable at compile time, but that's exactly what unknown plus a runtime check is for, not any.

Before
let result: any;
try {
  const obj = JSON.parse(raw);
  result = Array.isArray(obj) ? obj
    : obj.insights ?? obj.data
    ?? Object.values(obj)[0] ?? [];
} catch { result = []; }
After
let result: unknown[] = [];
try {
  const parsed: unknown = JSON.parse(raw);
  if (Array.isArray(parsed)) result = parsed;
  else if (parsed && typeof parsed === "object") {
    const obj = parsed as Record<string, unknown>;
    const c = obj.insights ?? obj.data ?? Object.values(obj)[0];
    if (Array.isArray(c)) result = c;
  }
} catch { result = []; }

MOD-09
apiFetch() had no top-level error handling — a dropped connection would throw uncaught
HIGH

Every call site assumed apiFetch() always resolves to { ok, data|error }. It didn't — a network failure (offline, DNS error, CORS block) threw before that shape was ever produced, and three separate call sites also cast URLSearchParams(params as any) to work around optional/typed query params.

Before
async function apiFetch<T>(path, init) {
  const res = await fetch(`${BASE}${path}`, {...});
  // no try/catch — throws on network failure
  return res.json();
}
// call sites:
apiFetch(`/projects?${new URLSearchParams(params as any)}`)
After
async function apiFetch<T>(path, init): Promise<ApiResponse<T>> {
  let res: Response;
  try {
    res = await fetch(`${BASE}${path}`, {...});
  } catch (err) {
    return { ok: false, error: String(err), statusCode: 0 };
  }
  return res.json();
}
function toQueryString(params?: Record<string, QueryValue>): string {...}
// call sites: apiFetch(`/projects${toQueryString(params)}`)

Functional Bugs

v0.4.0

Found during the first dedicated gap-analysis pass against the PRD — a mix of CSS invalidity, React lifecycle mistakes, and a route-prefix typo.

BUG-01
Blog post creation 404'd on every save — double-prefixed route
CRITICAL

The route was registered as POST /blog/admin inside a router already mounted at the /blog prefix, resolving to POST /blog/blog/admin. The client called POST /blog/admin — a guaranteed 404.

Before
app.post("/blog/admin",
  { preHandler: requireAuth },
  async (request, reply) => {...}
);
After
// prefix "/blog" already applied at
// registration → resolves correctly
app.post("/admin",
  { preHandler: requireAuth },
  async (request, reply) => {...}
);
BUG-02
Nav scroll background used invalid CSS
CRITICAL

rgba() cannot accept a CSS custom property as its r/g/b arguments — that's not how the function's grammar works. The frosted-glass scroll effect silently did nothing.

Before
background: scrolled
  ? "rgba(var(--canvas-rgb, 253,251,250), 0.94)"
  : "transparent",
backdropFilter: scrolled ? "blur(12px)" : "none",
After
background: scrolled ? "var(--canvas)" : "transparent",
backdropFilter: scrolled
  ? "blur(14px) saturate(1.6)" : "none",
WebkitBackdropFilter: scrolled
  ? "blur(14px) saturate(1.6)" : "none",
BUG-03
Scroll-reveal observer reconnected on every render
HIGH

Missing dependency array meant the useEffect ran after every render — disconnecting and recreating the IntersectionObserver even on unrelated state changes like a form keystroke, briefly losing observed state on every .reveal element.

Before
useEffect(() => {
  const observer = new IntersectionObserver(handleEntry, {...});
  document.querySelectorAll(".reveal")
    .forEach(el => observer.observe(el));
  return () => observer.disconnect();
}); // ← no deps array: runs every render
After
useEffect(() => {
  const io = new IntersectionObserver(handleEntry, {...});
  const observe = () => {
    document.querySelectorAll(".reveal:not([data-rv])")
      .forEach(el => { io.observe(el); el.dataset.rv = "1"; });
  };
  observe();
  const mo = new MutationObserver(observe);
  mo.observe(document.body, { childList: true, subtree: true });
  return () => { io.disconnect(); mo.disconnect(); };
}, []); // ← stable, runs once
BUG-04
D3 charts froze the wrong palette after a dark-mode toggle
HIGH

CSS custom properties were read once, at mount, and the resolved hex values baked directly into SVG attributes. Toggling dark mode changed the variables but not the already-painted chart.

Before
useEffect(() => {
  const brand = getCSSVar("--brand");
  // ...draws chart using `brand`, once
}, [data]); // dark mode not in deps
After
function useDarkMode(): boolean {
  const [dark, setDark] = useState(false);
  useEffect(() => {
    const check = () => setDark(
      document.documentElement.classList.contains("dark"));
    check();
    const mo = new MutationObserver(check);
    mo.observe(document.documentElement,
      { attributes: true, attributeFilter: ["class"] });
    return () => mo.disconnect();
  }, []);
  return dark;
}
// in each chart:
const dark = useDarkMode();
useEffect(() => {...}, [data, dark]); // redraws on toggle

BUG-06
Admin session silently dropped on every page refresh
HIGH

The access token lived only in a module-level JS variable. Any hard refresh cleared it; the dashboard would then flash logged-out before the silent-refresh-from-cookie flow could complete.

Before
let _accessToken: string | null = null;
export function setToken(t: string | null) { _accessToken = t; }
export function getToken() { return _accessToken; }
// gone on every reload
After
let memoryToken: string | null = null;
export function setToken(t: string | null) {
  memoryToken = t;
  try {
    if (t) sessionStorage.setItem("__dc_at", t);
    else sessionStorage.removeItem("__dc_at");
  } catch {}
}
export function getToken() {
  if (memoryToken) return memoryToken;
  try {
    const cached = sessionStorage.getItem("__dc_at");
    if (cached) { memoryToken = cached; return cached; }
  } catch {}
  return null;
}
